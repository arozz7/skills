# ui-design

Design and build screens that feel like one family while each app keeps its own identity. **The app's own tokens and `DESIGN.md` are the brief.** Refine before you redesign. Default mode is **Operate** (a tool used for long sessions): scanability and consistency outrank expression. This skill is self-contained for the rules; it carries no colour values (see "New app").

## Read first (stop when you have enough)
1. The app's `DESIGN.md`. If there is none, say so and offer to write one (see "New app"); do not invent one silently. If it records a guidelines version other than v0.2, say so.
2. The app's token file and theme code, and `package.json` (React version, Tailwind or plain CSS, Tauri or Electron). Detect the stack; never assume it. For a new app with no files, ask the user for the stack (Tauri or Electron, React, Tailwind or plain CSS).
3. The shell settings that set the window (minimum size, saved position) and the current layout CSS.

## Steps
1. **State the job:** who uses this screen, the one primary action, the mode (Operate unless told otherwise). If the request leaves Operate (a landing page, a first-run screen), say so and confirm before going expressive; tokens and the contrast floor still apply.
2. **Layout** from the shell and screen layouts below; reuse the app's existing regions and components before making new ones.
3. **Size first.** State the app's minimum window and the width class each region collapses in (Wide, Medium, Compact). Build flexible layouts; never a fixed-width shell. Say which sizes you checked and which you did not (if you cannot run the app, say so and name what you read instead).
4. **Tokens only.** Use the vocabulary names, or the app's *current* names until its retrofit is done (its `DESIGN.md` carries the map; with none, the app is before its retrofit). Never a raw hex, never a new colour. Do not add themes; that is the retrofit request's job.
5. **Every interactive element gets its states:** rest, hover, pressed, focus, disabled, and error where it takes input. **Every screen gets its empty, loading and error states** (what is missing or failed, and the next step).
6. **Components and libraries:** use what the app already has. If a new dependency seems needed, hand over to `ui-library-picker`; do not add one yourself.
7. **Accessibility floor:** keyboard reachable, visible focus, accessible names on icon-only controls, status as symbol plus word plus colour, reduced motion respected, targets at least 24 px.
8. **Output:** a short design note (job, layout and size classes, states, tokens used, anything the app lacks) and then the implementation. Record any rule you had to bend as a **deviation** line for the app's `DESIGN.md`; do not bend silently.

## New app (no `DESIGN.md` yet)
Propose one before designing, with these parts: the themes it offers from the shared set (Graphite, Light, Sand) and its default; whether "follow the system" is offered; the accent as a dark and a light value in one `light-dark()` declaration, both tested at 4.5:1; the neutral `stage` if it shows photos or a canvas (ask whether the optional white surround is wanted); Inter and lucide; the minimum window and the collapse order; a Deviations table (rule, what the app does instead, reason, date); the guidelines version followed (v0.2). **Token values are not in this skill:** take the shared Graphite, Light and Sand theme blocks from the user (their shared theme file) and never invent hex values; the accent pair is the app's own and must be tested at 4.5:1.

## The rules
**Tokens (18):** `surface-0` page, `surface-1` panels, `surface-2` toolbar, raised cards, dialogs, menus, `surface-3` neutral hover fill; `border`, `border-strong` (control outlines, 3:1); `text-primary`, `text-secondary`, `text-tertiary` (all 4.5:1); `accent`, `accent-contrast`, `accent-subtle` (selection tint); `success`, `warning`, `danger`, `info` (always symbol plus word); `scrim`; `stage` (image backdrop, a neutral grey, never tinted). An app keeps its own extra tokens (severity, charts, brand) beside these.
**Themes:** shared set Graphite (dark, neutral), Light, Sand (warm light); `data-theme` on the root plus `color-scheme`; each app lists the themes it offers and its default. The accent is a dark and a light value (`light-dark()`), never signals status, and stays at least 40 (RGB) away from every status colour.
**Derived states:** button hover mixes the fill toward `text-primary` by 12 percent (accent) or 8 (neutral), pressed 24 or 16; row, sidebar and menu hover is a faint 5 percent step; **selected is the accent tint plus a 3 px bar and always reads stronger than hover**; a hovered selected row shifts the tint 6 percent. Focus is a 2 px accent ring offset 2 px. Disabled is half opacity, no hover, no pointer.
**Scales:** type 11/16 caption, 13/18 body, 14/20 control, 16/22 heading, 20/26 title (Inter; system mono; tabular figures for numbers); spacing 4 px base (4, 8, 12, 16, 24, 32, 48); radius 4 inputs, 8 buttons and menus, 12 dialogs and cards; elevation none, floating, dialog (depth from surface steps first); motion only `transform` and `opacity`, 100 to 120 ms hover, 160 to 200 ms panels, reduced motion respected; density Comfortable (control 32, row 36) and Compact (control 26, row 28), colour never changes with density; icons lucide, 16 px in controls, 20 in navigation.
**Interaction:** keyboard first; one shortcut sheet on `?`; feedback ladder inline message < toast < banner < dialog; dialogs state the action, one sentence of consequence, safe button focused, destructive button names what it does; prefer undo to a confirm (if the user explicitly asks for a confirmation dialog, build it and mention the undo alternative once); forms label above, hint below, error replaces the hint, validate on blur, never clear input; long work shows progress with Cancel and the app stays usable; numbers and dates use locale formatting.
**Shell layout (comfortable px):** header 40; sidebar 220 (rail 52); toolbar 40; content (grid, list, table or stage); inspector 280, collapsible; status line 24 (left what is happening, right counts, zoom, progress). Library plus detail: filter bar, thumbnail grid or film strip, large neutral stage, decision bar with shortcuts on the buttons. Settings: a section list left, the section right; theme and density radios under Appearance. Table: sortable header, hover row, selected row (tint plus bar), tabular figures, status as symbol plus word.
**Window sizes, resolution and scaling (never assume a maximised window):** logical px. Declare a minimum window (default 640 x 480; a higher one is a recorded deviation). Width classes: **Wide** 1200 and up (full shell), **Medium** 840 to 1199 (inspector becomes an overlay panel from the toolbar), **Compact** below 840 (sidebar becomes a rail, inspector overlay, toolbar overflow into a "more" menu); components respond to their pane's own width. No fixed-size content regions; panes have a minimum, are resizable and remembered; no fixed pixel height on text; the page never scrolls sideways, content scrolls inside its region and the chrome stays; wide tables scroll in their own container. Long names truncate with an ellipsis, and the full value is available in a tooltip, in the accessible name and in the inspector; dialogs, menus, popovers and toasts stay inside the window (a 16 px margin on every side, own scroll; header and footer fixed, body scrolls). Large monitors: grids add columns, reading text and forms stay about 80 characters or 720 px wide, the UI does not scale up. Usable with larger OS text and 200 percent zoom in a 1280 px window. Photo and canvas apps: "100 percent" is one image pixel per device pixel (CSS size = image size divided by `devicePixelRatio`), render at device resolution, re-render when the window moves to another monitor. Remember window size, position and maximised state (in the app's existing settings storage, saved after a resize or move with a short debounce, restored bounds kept apart from the maximised state), and on start place the window on a visible monitor if the saved one is gone and clamp it to the minimum window. Mouse and keyboard first, but 24 px targets in every density and nothing hover-only. Mobile is not designed for. Collapse order: navigation to an icon rail, inspector or settings to a drawer, secondary toolbar buttons into a "More" menu, strips shrink then go, bottom sheet under 800 px. Nothing becomes unreachable: whatever leaves stays reachable by a visible, keyboard-reachable control, and navigation is never simply removed. A control the app needs that is not in the standard set is built app-level, recorded in its design note and proposed for sharing; it is not copied to other apps.

## Do not
Add a library, install anything, write a raw colour, use one-off sizes, put settings in a modal, assume a full-screen window, or redesign what only needed a refinement. If something is missing from these rules, say so to the user as a finding rather than improvising.
